# Design Note

## Evidence-led design decisions

This implementation is intentionally not described as a fully deterministic or universally grounded support system. Its behavior was tested against the supplied dataset, and the design reflects the failures that appeared there.

The clearest retrieval failure was `triage_01_clean_baseline` (`TKT-10000`), a DataBridge Pro request for bulk archive operations. The session's relevance assessment was `0.63`, and the returned citation was the cross-product SSO troubleshooting section, “Scope Errors (`403 Forbidden: insufficient_scope`)”. That was not guessed from the ticket: a direct BM25 inspection put that chunk first, ahead of the DataBridge Pro document. The issue is lexical overlap across a small corpus, especially generic operational vocabulary, rather than a fabricated path. The current retrieval guard scopes out other product documents when exactly one product is named, but cross-product troubleshooting documents remain eligible and can still win. The sample output in the README makes this limitation visible instead of presenting retrieval as validated merely because the cited file exists.

The evaluator had a separate, concrete source-context bug. `_account_source_context()` initially omitted account fields that the account-brief generator was allowed to use. As a result, the Mistral judge could mark a grounded statement such as `open_tickets: 9` as fabricated because that fact was absent from the judge's own context. The fix was to pass the same relevant account facts—plan tier, health status, usage trend, open-ticket count, recent P1 count, and NPS score—to the judge. This was an evaluation-input defect, not an inference about model quality.

Provider reliability also affected the observed results. The captured evaluation report recorded eight failures such as `RetryError(<Future ... raised RateLimitError>)`, including `triage_01` and `brief_01`. The original retry boundary converted the exhausted Groq 429 into Tenacity's wrapper exception, so the intended fallback could not recognize it. The corrected implementation retries the lower-level Groq call, preserves the final `GroqRateLimitError`, then logs `Groq rate-limited after exhausting all retries ... failing over to OpenRouter ...` before making one fallback call. It logs a separate success or failure line for that fallback. This is deliberately narrow: authentication and request errors do not fail over, and streaming calls do not change providers mid-response.

The determinism claim was narrowed after live testing. Temperature `0` and a fixed seed did not make `executive_summary`, `talking_points`, or even free-text risk labels word-for-word stable. For example, the same risk may be labeled “Consecutive P1 tickets” or “Consecutive P1 incidents”. It would be an overclaim to test full JSON equality. What is required and verified is the safety-critical field: each quote must be a verbatim source substring, and the sorted quote values are stable across repeated runs. The live `ACC-7397` output demonstrates this distinction with the exact escalation-note quotes retained in `risk_flags`.

## Latency and quality

The conceptual triage pipeline is classify, retrieve, route, then draft; the current implementation retrieves before its combined classify-and-draft LLM call so the draft can use the selected snippet. Routing is local Python logic after classification. Under a hard latency SLA, I would keep schema validation and deterministic routing, return the classification first, and make the prose draft and judge scoring optional or asynchronous. I would also return no KB citation rather than wait for a weak or ambiguous match. Cutting quote verification would be the wrong trade: it is cheap and protects the most consequential account-brief claims.

## Data sensitivity and PII

The provided data is synthetic, but its fields resemble production support data: company names, contact names, escalation notes, ticket bodies, account health, and renewal context. A real deployment needs tenant isolation, access control by support role, encryption in transit and at rest, retention/deletion policies, provider data-processing agreements, redaction or minimization before external LLM calls, and auditable access logs. Prompts and evaluation artifacts must not become an uncontrolled store of customer text.

## Scaling to 10x

One premise needs correction from the implementation: the current code uses a BM25 index, not TF-IDF, and `_get_retriever()` caches it once per process rather than rebuilding it per request. At 10x traffic, the first real bottleneck is therefore synchronous provider latency and retry backoff inside a single FastAPI worker, not index construction. Concurrent requests will queue behind blocking Groq calls; a 429 can add three retries and a fallback HTTP request. The next steps are multiple workers or an async job boundary, connection pooling and bounded concurrency for providers, timeouts/circuit breaking, and an externally managed or shared retrieval index if the corpus grows or workers multiply.
